# 微信邀请统计 XML 兼容修复设计

## 问题与证据

微信 4.1.12.26 在 `delchatroommember` 系统消息中出现了两种现有解析器未完整覆盖的结构：

1. 本人一次邀请多人时，`plain`/`text` 只用一对引号包住所有姓名，姓名之间用顿号分隔；`memberlist` 则包含同等数量、顺序对应的 `username`。当前实现按引号提取，因此把整串姓名当成一个人，并只使用第一个 wxid。
2. 扫描本人分享二维码入群时，`scene` 为 `qrcode`，正文为 `“某人”通过扫描你分享的二维码加入群聊`。当前本人 XML 分支只接受 `scene=invite`，普通二维码正则又要求分享者是带引号的人名，因此该消息进入“未解析”。

真实群 `57757918914@chatroom` 已确认：本人两条直接邀请 XML 分别包含 24/24 和 2/2 个姓名与 wxid；另有 17 条“你分享的二维码”消息。修复前页面显示本人“直接 2、二维码 0”。

## 方案比较

### 方案 A：在核心 XML 解析层原子化事件（采用）

- 当单个引号块对应多个 `memberlist/username` 时，按微信使用的顿号/中文逗号拆分。
- 只有拆分后的姓名数与 wxid 数完全一致时才按位置绑定，避免猜测身份。
- 识别 `scene=qrcode` 且正文明确包含“你分享的二维码”，把分享者标记为本人，并保留入群者 wxid。
- CLI、Web、文本/CSV/JSON 导出共用同一结果，无需分别修补。

优点是统计口径统一、身份稳定、改动集中；缺点是需要新增 XML 模板回归测试。

### 方案 B：只在网页展示层拆分姓名

能够让页面数字看起来正确，但 CLI、导出和身份去重仍然错误，也无法处理本人二维码归属，因此不采用。

### 方案 C：按截图中的具体姓名或群聊做数据补丁

能快速改变当前结果，但无法适配其他电脑或后续新消息，且不可审计，因此不采用。

## 数据流与行为

解析器仍输出“一位邀请人 + 一位被邀请人”的原子事件。对批量直接邀请，姓名与 wxid 完全等长时逐项生成事件；若不等长，继续保留原有保守行为，不制造错误绑定。对“你分享的二维码”，事件方法为 `qr`，邀请人通过 `chat_ctx.self_username` 解析为当前微信账号，被邀请人使用 XML 的 `memberlist` wxid。

排行继续按被邀请人稳定身份键去重。现有网页会自然显示逐人明细；折叠标题中的人数、直接邀请数、二维码数与展开明细保持一致。未解析队列不再包含已识别的本人二维码消息。

## 验收标准

- 两人批量 XML 生成两条直接邀请事件，并按顺序绑定两个 wxid。
- `scene=qrcode` 的“通过扫描你分享的二维码”生成一条归属于本人的二维码事件。
- 聚合结果中本人名称和 wxid 解析为本地账号，详情、排行、CLI 与 Web 使用相同统计。
- 当前真实群中 Au Revior 校正为直接邀请 26 人、二维码 17 人；这些记录不再显示为“未解析”。
- 定向测试、全量测试、打包后 CLI 与本地 Web 验收均通过。
