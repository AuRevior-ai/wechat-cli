# WeChat CLI 外部记忆治理设计

日期：2026-08-07  
状态：已批准，等待实施计划  
范围：项目文档、状态入口与历史记录治理；不修改业务代码、授权协议、更新逻辑或云端资源

## 1. 背景

WeChat CLI 已从本地微信数据查询工具发展为包含 Windows Launcher、许可证、设备授权、签名更新、自动回滚、管理员工具、发布工具和 Cloudflare Worker 的产品化工程。代码实现和测试总体完整，但外部记忆存在以下问题：

- 当前路线图和板块 4 实施计划仍是未跟踪文件，尚未进入 Git 历史；
- README 仍主要描述旧的公共 CLI 和 npm 0.2.4 路线，与 Windows/Python 0.5.0 主工程不一致；
- 多份已经实施完成的施工计划仍保留大量未勾选项目，容易被误读为当前完成度；
- 历史验收报告与当前状态缺少明确边界；
- 缺少项目级入口文件，新会话无法稳定发现当前权威状态；
- 缺少统一 Changelog 和版本、源码、发布记录之间的说明；
- 云端事实与仓库内可复验事实没有清晰区分。

本设计建立一套轻量、可维护的外部记忆层级，使新会话、维护者和发布流程能够快速判断当前事实、历史事实和下一步工作。

## 2. 目标

本次治理需要达到以下结果：

1. 新会话从仓库根目录最多经过两次文档跳转即可定位当前项目状态和唯一下一步。
2. 当前状态、专项路线、历史设计、施工计划和验收报告各自承担单一职责。
3. README 中的仓库地址、主版本、命令清单、平台支持和分发渠道与当前代码一致。
4. 明确 npm 0.2.4 与 Windows/Python 0.5.0 是不同阶段或渠道，避免误认为版本同步。
5. 历史施工计划不再被当作实时进度看板。
6. 历史报告保留原始时间点事实，同时清楚标出后续状态入口和已解决事项。
7. 当前两个未跟踪的权威文档纳入 Git 管理。
8. 不编造仓库外许可证、Cloudflare、GitHub Release 或生产状态。

## 4. 外部记忆权威层级

### 4.1 根目录 `AGENTS.md`：会话入口

`AGENTS.md` 是任何开发会话进入仓库后的第一入口。它只保存稳定规则，不复制易变化的项目状态。

它应规定：

- 先读取 `docs/PROJECT_STATE.md`；
- 涉及授权、更新、Cloudflare、GitHub Release、Windows 安装或上线时，再读取 `docs/deployment/authorized-update-roadmap.md`；
- 当前实施任务存在独立计划时，继续读取路线图指定的计划；
- `docs/superpowers/specs/` 是已批准设计依据；
- `docs/superpowers/plans/` 是施工计划，不默认代表当前完成度；
- `docs/deployment/*report.md` 是时间点验收快照；
- 不覆盖未提交工作，不泄露凭据，不擅自执行外部副作用。

### 4.2 `docs/PROJECT_STATE.md`：当前状态唯一摘要

该文件是整个仓库的当前状态摘要，面向新会话和维护者。它只记录当前可确认事实，不保存完整历史。

内容包括：

- 当前应用版本、Launcher 版本和产品标识；
- 当前主分支和基线提交；
- 当前专项板块及唯一允许推进的下一步；
- 当前 Git 工作树中已知的外部记忆文件；
- 最近一次本地验证结果；
- 已知风险和阻塞；
- 当前状态的更新时间；
- 指向专项路线图、当前实施计划和最近验收报告的链接；
- “仓库内可复验事实”和“上次人工验收记录”的明确区分。

当仓库无法验证某项云端状态时，使用“上次记录为……”而不是“当前一定为……”。

### 4.3 专项路线图：授权更新项目权威记录

`docs/deployment/authorized-update-roadmap.md` 继续作为授权、更新、发布和上线专项的权威路线图，保留固定七板块结构。

它负责：

- 板块状态；
- 当前检查点；
- 进入条件；
- 外部副作用授权门槛；
- 非敏感证据标识；
- 当前专项唯一下一步。

`PROJECT_STATE.md` 只摘要引用，不复制整套七板块内容。

### 4.4 历史资料层

以下文件属于历史依据，不承担整个项目的当前状态：

- `docs/superpowers/specs/`：已批准设计和决策依据；
- `docs/superpowers/plans/`：实施时的施工计划；
- `docs/deployment/*report.md`：特定日期的验收快照；
- `CHANGELOG.md`：按版本记录用户可感知变化和重要架构变化。

## 5. README 治理

中英文 README 继续作为产品说明和使用入口，不记录实时开发进度。

### 5.1 必须同步的事实

- 仓库地址改为当前远端 `AuRevior-ai/wechat-cli`；
- 主工程版本说明为 0.5.0；

- 补充 `ai-package`、`invite-stats`、`media` 和 `web` 等当前命令；
- 说明 Windows、macOS 和 Linux 的能力与分发差异；
- 说明 Windows 0.5.0 产品化路线包含 Launcher、许可证和签名更新；
- 保留 Apache-2.0 许可事实，但清楚说明私有发布与授权服务不等同于所有发行渠道都公开可下载。

### 5.2 npm 0.2.4 与主工程 0.5.0

README 应明确说明：

- `npm/wechat-cli/package.json` 当前仍为 0.2.4；
- Python/Windows 主工程当前为 0.5.0；
- 两者当前不是同步版本线；
- npm 安装说明只适用于现有 npm 渠道和其已发布平台包；
- 不声称 npm 已提供 Windows 0.5.0 商业桌面包；
- 后续是否统一版本线属于独立发布决策，不在本次治理中处理。

### 5.3 README 不承担的内容

README 不记录：

- 当前正在执行哪一个 Task；
- Cloudflare Secret 数量；
- 当前许可证或设备状态；
- GitHub Draft Release 的实时状态；
- 临时哈希、请求 ID 或外部副作用授权记录。

这些信息分别进入 `PROJECT_STATE.md`、专项路线图或验收报告。

## 6. CHANGELOG 设计

新增根目录 `CHANGELOG.md`，按版本整理当前可从 Git、代码和已有文档确认的变化。

### 6.1 记录范围

- 0.5.0：许可证、设备授权、离线租约、Launcher、签名更新、回滚、管理员/发布 CLI、Worker、Windows 安装迁移；
- 0.4.x：AI 资料包、作者支持页、Web 使用体验和 Windows 打包演进；
- 0.2.x 至 0.3.x：邀请统计、聊天总结、导航和选择器等可确认变化。

### 6.2 记录原则

- 不把未完成的 0.5.1 写成已发布；
- 不编造旧版本准确发布日期；
- 无法精确归属的历史内容标为“根据现有提交与文档整理”；
- Changelog 面向功能变化，不代替专项路线图；
- 每个版本可关联主要提交或设计文档，但不要求逐提交罗列。

## 9. 事实与证据边界

文档中的状态分成两类：

### 9.1 仓库内可复验事实

例如：

- `APP_VERSION = 0.5.0`；
- Launcher 版本 0.1.0；
- 模块和测试文件存在；
- 当前 Git 提交；
- 0.5.0 本地 ZIP 的大小和 SHA-256；
- staging 配置中的 Worker、D1 和 R2 名称；
- 当前 bootstrap 仍包含 Demo URL 和 Demo 公钥；
- Python 与 Worker 本地测试结果。

这些事实可以使用确定语气。

### 9.2 仓库外人工验收记录

例如：

- Worker 是否仍在线；
- Secret 是否仍存在；
- GitHub Draft Release 是否仍存在；
- D1 当前记录；
- 测试许可证是否已创建；
- 设备和租约当前状态。

这些事实若未在本次任务中通过授权工具重新验证，应表述为“路线图上次记录为……”并附记录时间。

## 11. 验证标准

实施完成前必须执行并读取结果：

1. 文档入口检查：从 `AGENTS.md` 可定位 `PROJECT_STATE.md` 和专项路线图；
2. Markdown 相对链接检查；
3. README 命令清单与 `python -m wechat_cli.main --help` 一致性检查；
4. README、`pyproject.toml`、`wechat_cli/version.py` 和 npm 包版本关系检查；
5. 机密模式扫描，确认没有 Token、私钥、完整许可证或 `.env` 内容进入文档；
6. `python -m unittest discover -s tests -q`；
7. Worker `npm run typecheck`；
8. Worker `npm test -- --run`；
9. `git status --short`、`git diff --stat` 和相关文件完整差异审查。

已知 `unittest` 可能在测试过程中输出缺少 `pywebview` 的构建探测信息；只要测试最终状态为 `OK`，该信息不等同于测试失败，但应在验证报告中如实记录。
